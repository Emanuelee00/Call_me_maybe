# call me maybe

## Description

`call me maybe` turns natural-language prompts into structured function
calls. Given a question like *"What is the sum of 40 and 2?"*, the program
does not answer `42` — it outputs which function to call and with which
typed arguments:

```json
{"prompt": "What is the sum of 40 and 2?", "name": "fn_add_numbers", "parameters": {"a": 40, "b": 2}}
```

The function name and every argument are generated by a small local LLM
(`Qwen/Qwen3-0.6B`, 0.6B parameters) using **constrained decoding**: at
every generation step, invalid tokens are masked out before the model
picks the next one, so the output is guaranteed to be valid JSON that
matches the expected schema — instead of hoping the model "gets it right"
from prompting alone.

## Terminology

- **Tensor**: the array data structure PyTorch (and most ML frameworks)
  uses to store numbers — a generalization of scalars/vectors/matrices to
  any number of dimensions. `Small_LLM_Model.encode()` returns a 2-D
  tensor of shape `(1, sequence_length)`: one row (batch size 1) holding
  the token ids, because the model expects input in that exact shape.
- **PyTorch**: the machine learning library `llm_sdk` uses (`import
  torch`) to load `Qwen/Qwen3-0.6B` and run it. It stores data as
  tensors and runs the model's forward pass — the single expensive
  operation the pipeline calls repeatedly through
  `get_logits_from_input_ids`.
- **LLM SDK** (`llm_sdk`): the wrapper package provided for this
  project, built on top of PyTorch and Hugging Face `transformers`. It
  exposes one class, `Small_LLM_Model`, and this project only ever calls
  four of its methods: `encode` (text → token id tensor), `decode`
  (token ids → text), `get_logits_from_input_ids` (one forward pass →
  next-token logits), and `get_path_to_vocab_file` (path to the
  tokenizer's vocabulary file). Everything else about the underlying
  model — weights, tokenizer internals, device placement — stays hidden
  behind it; the subject also forbids reaching past it into any private
  attribute.
- **GPU vs. CPU**: a CPU (Central Processing Unit) is a general-purpose
  processor with a handful of powerful cores, built to do varied,
  branching, mostly sequential work well. A GPU (Graphics Processing
  Unit) has thousands of smaller, simpler cores, built to do the *same*
  arithmetic operation on huge numbers of values at once — originally
  for computing color/depth for millions of pixels in parallel. Running
  a model is dominated by matrix multiplications (the core operation
  inside every transformer layer, i.e. exactly "the same operation,
  applied massively in parallel"), which maps onto a GPU's thousands of
  cores far better than onto a CPU's few.
- **CUDA**: NVIDIA's parallel-computing platform — the API that lets
  code (via PyTorch here) run computations on an NVIDIA GPU's cores
  instead of the CPU's. NVIDIA GPUs dominate ML workloads mostly because
  virtually every deep learning framework, PyTorch included, is built
  and heavily optimized on top of CUDA, plus dedicated **Tensor Cores** —
  hardware units built specifically for the matrix-multiply-accumulate
  operations neural networks need, at reduced precision (fp16/bf16) for
  speed. `Small_LLM_Model.__init__` picks `cuda` (or Apple's `mps`)
  automatically over `cpu` whenever one is available — see Performance
  and reliability for what that meant on the machine this ran on, and
  for the memory numbers behind why large models need this hardware.
- **RAM vs. VRAM**: RAM (Random Access Memory) is the system memory that
  sits next to the CPU and holds whatever the CPU is currently working
  with. VRAM (Video RAM) is the same kind of memory, but built onto the
  GPU board instead, physically much closer to its cores and much
  faster for them to read from — it holds whatever the GPU is currently
  computing on. When `Small_LLM_Model` runs on `cuda`,
  the model's weights are loaded into VRAM, not RAM; on `cpu`, they sit
  in ordinary RAM instead. This is why VRAM size (not RAM size) is what
  actually caps how large a model a given GPU can run — see "Model size
  vs. hardware requirements" for the concrete numbers.
- **Logits**: the raw, pre-softmax scores the model outputs for every
  token in its vocabulary at each step — higher means the model thinks
  that token is more likely to come next.
- **Greedy decoding**: always picking the token with the highest logit
  (`masked_argmax`), with no sampling and no randomness — the same input
  ids always produce the same output.
- **BPE / subword tokenization**: the algorithm behind the tokenizer's
  vocabulary. Starting from individual bytes, it repeatedly merges the
  most frequent adjacent pair seen in a large text corpus into one new
  token, until a fixed vocabulary size is reached (Qwen3 uses ~150k
  tokens). The result is subword units: common whole words get a single
  token, rarer words get split into smaller frequent pieces, and any
  string can still be represented, since single bytes are always in the
  vocabulary as a fallback. We don't choose BPE — it's baked into the
  Qwen3 tokenizer — but it directly caused the hardest bug in this
  project: because BPE merges frequent adjacent characters, a closing
  `"` followed by a comma (very common in JSON) gets merged into one
  single token (`'",'`) in the vocabulary, distinct from the lone `"`
  token. See Challenges faced.
- **Constrained decoding**: masking invalid vocabulary tokens (setting
  them out of consideration) *before* argmax at every generation step,
  so the output is guaranteed to match a schema — instead of generating
  freely and validating afterwards.
- **Character class (regex)**: the set of characters allowed for a given
  parameter type, expressed as a regex character class (e.g. `[0-9.]`
  for numbers, `[^"]` for strings) and used by `get_filtered_tokens_vocab`
  to keep only the vocabulary tokens that are made entirely of allowed
  characters.
- **Stop token set**: the set of token ids that end a generated value
  (`get_stop_token_ids`) — a set rather than one exact id, precisely
  because of BPE fusion above: several different tokens can all
  correctly signal "stop here".
- **Prompt priming vs. token forcing** — the two different ways this
  project puts tokens into the sequence, used for two different reasons:
  - *Priming* means writing already-known, fixed text straight into the
    token ids with `encode_to_ids`, with **no model call at all**. It is
    used wherever the exact text is fully determined by the JSON syntax
    or by the schema, so there is nothing for the model to decide: the
    JSON punctuation (`", "parameters" : {`, `, `, `}}`), each
    parameter's key (`f'"{key}": '`), and the quotes around a string
    value.
  - *Forcing* means the constrained-generation loop (`constrain_functions`,
    `constrain_value`): the content genuinely depends on the model —
    which function, which value — so every token needs one real call to
    `get_logits_from_input_ids` (a full forward pass through the
    network), masked down to only the valid candidates.
  - **Why it saves cost**: a forward pass is the expensive part of the
    whole pipeline. Priming skips it completely for spans that are
    already 100% determined. Measured directly on the full 11-prompt run
    (instrumenting both call sites): **124 model forward passes** were
    needed for genuinely model-decided tokens (function names +
    parameter values), against **192 tokens** written by priming with
    **zero** model calls — i.e. more tokens were produced for free by
    priming than were generated by forcing, for this workload.
- **Transformer**: the neural network architecture behind `Qwen3` (and
  virtually every modern LLM). Its key building block is
  *self-attention*: for every token, it computes how much every other
  token in the sequence should influence it, so relationships between
  words are weighed regardless of how far apart they are — unlike
  older architectures (e.g. RNNs) that read tokens strictly in order
  and struggled to keep far-back context relevant. This project never
  touches transformer internals directly — from the outside,
  `get_logits_from_input_ids` is exactly "run the whole sequence
  through the transformer once, get back logits for the next token";
  everything internal to that call stays behind `llm_sdk`.
- **LLM (Large Language Model)**: a transformer trained on huge amounts
  of text to predict the next token, then scaled up in parameters and
  training data until that single next-token-prediction skill starts
  generalizing to tasks it was never explicitly trained for —
  translation, summarization, or the function-calling this project
  does — just from being prompted differently. That is the key
  difference from a "traditional" narrow ML model (e.g. a spam
  classifier or a sentiment analyzer): a narrow model is trained for
  one fixed task and can't be repurposed without retraining, while an
  LLM is repurposed just by changing the input text. `Qwen/Qwen3-0.6B`
  is "small" only relative to other LLMs — it is still a
  general-purpose next-token predictor, not a model built to output
  JSON. That gap between "general-purpose text predictor" and "this
  project's narrow, fixed schema" is exactly why constrained decoding
  is needed at all, instead of trusting the model to stay on schema by
  itself.

## Algorithm explanation

For each prompt, `src/pipeline.py`'s `process_prompt` runs the following
steps:

1. **Build the prompt** (`src/prompt.py`): the available functions are
   rendered as a plain-text list and appended to the user's question,
   followed by the opening of the expected JSON (`{"name": "`).
2. **Constrain the function name** (`constrain_functions` in
   `src/constrained_decoding.py`): tokens are generated one at a time,
   but at each step only tokens that keep the generated prefix a valid
   *prefix of one of the known function names* are allowed as candidates.
   Generation stops as soon as the prefix exactly equals one full name.
   This is what guarantees the function is chosen by the LLM itself, not
   by a heuristic — the model is only ever prevented from inventing a
   name that doesn't exist.
3. **Constrain each parameter value** (`generate_parameters` /
   `constrain_value`): depending on the parameter's declared type, only
   certain vocabulary tokens are allowed at each step — digits/`.`/`-`
   for numbers, anything but a quote for strings. Booleans reuse the same
   prefix-matching mechanism as function names, against `["true",
   "false"]`.
4. **Stop condition**: generation for a value stops when the model picks
   a token from a *set* of stop tokens, computed by `get_stop_token_ids`
   (see Challenges faced below) — not just a single exact token id.
5. The accumulated token ids are decoded back to text and parsed as
   JSON.

Everywhere a choice is made, invalid vocabulary tokens are masked to
`-inf` before argmax (`masked_argmax`) rather than sampled and validated
after the fact — so the model is structurally unable to produce broken
JSON or an out-of-schema value.

## Code flow (worked example)

Tracing the actual function calls for one prompt, `"What is the sum of 2
and 3?"`:

1. `src/__main__.py: main()` loads and validates both input files with
   `load_and_validate_definitions` (pydantic), creates the `Small_LLM_Model`,
   loads the vocabulary once (`load_vocab` → a `Vocab`), and precomputes
   `valid_tokens_for_name_func` — the `a-zA-Z0-9_` token set reused for
   every prompt.
2. `build_system_prompt` + `format_functions_list` turn the function
   definitions into one text block, computed once for the whole run
   (`"Available functions:\n- fn_add_numbers(a: number, b: number): ..."`).
3. `main()` calls `pipeline.process_prompt(model, vocab, functions,
   formatted_functions, valid_tokens_for_name_func, prompt.prompt)` for
   this prompt.
4. `build_full_prompt` appends the user's question and **primes** the
   opening of the expected JSON, `{"name": "`, onto the system prompt.
5. `encode_to_ids` tokenizes that whole block once — one tokenizer call,
   still zero model forward passes.
6. `constrain_functions` **forces** the function name (mechanism: see
   Algorithm explanation, step 2) — repeated `get_logits_from_input_ids`
   + `masked_argmax` calls until the prefix exactly equals
   `"fn_add_numbers"`.
7. `add_parameters_to_ids` **primes** `", "parameters" : {` — no model
   call.
8. `generate_parameters` walks the two `number` parameters, `a` and `b`
   (mechanism: see Algorithm explanation, step 3): for each, it
   **primes** the key (`"a": `) then **forces** the value with
   `constrain_value` — here the model picks `2`, then a stop token; it
   **primes** `, ` between the two parameters and `}}` at the end.
9. `model.decode(current_ids)` turns the whole id sequence back into
   text; `json.loads` on the substring starting at `{"name"` parses it —
   guaranteed to succeed, since every character was either literal
   (primed) or came from a masked, schema-respecting candidate (forced).
10. `process_prompt` returns `{"prompt": ..., "name": ..., "parameters":
    ...}`; `main()` collects every prompt's result and writes the list to
    `data/output/function_calling_results.json`.

## Design decisions

- **Module split**: the code is split by responsibility instead of one
  big file — `vocab.py` (tokenizer vocabulary, wrapped in a pydantic
  `Vocab` model), `prompt.py` (building the text prompt),
  `constrained_decoding.py` (the masking/generation primitives),
  `pipeline.py` (orchestration for one prompt), `models.py` (pydantic
  schemas for input/output), `utils.py` (input loading/validation).
- **Generic input loading**: `load_and_validate_definitions` is generic
  over any pydantic model (`TypeVar("T", bound=BaseModel)`), so it is
  reused for both function definitions and prompts while keeping full
  static typing (no `list[BaseModel]` widening).
- **Per-prompt isolation**: `src/__main__.py` wraps each prompt's
  processing in its own `try/except`, so one failing prompt is skipped
  (with a printed reason) instead of crashing the whole batch.

## Performance and reliability

On the provided `data/input/function_calling_tests.json` (11 prompts),
the pipeline gets **11/11 correct** — right function name and right,
correctly-typed arguments for every prompt — and every output is valid,
schema-matching JSON by construction (constrained decoding, not just
prompting). A full run over all 11 prompts, including loading the model,
takes about **9 seconds**. `Small_LLM_Model` auto-selects the fastest
available device (`mps` > `cuda` > `cpu`); on the machine this was timed
on, that meant it ran on an NVIDIA RTX 4050 Laptop GPU (6 GB VRAM), not
the CPU — see "Model size vs. hardware requirements" below for how much
smaller this model's resource footprint is than a large hosted model's.

### Why a 0.6B model reaches near-100% reliability here

Prompted directly, small models are notoriously bad at producing valid
structured output — the subject itself cites ~30% success rates. Here
structural validity (valid JSON, right keys, right types) is **not**
coming from the model's competence at all: it is enforced by masking,
so an invalid character, wrong key, or unknown function name is simply
never a candidate at any step — the model cannot get that part wrong,
regardless of how weak it is.

What is left to the model is a much narrower decision than "write a
whole JSON document": at each step it only has to pick among a handful
of already-valid candidates (e.g. "which digit", "which function
name prefix continues correctly") instead of the full ~150k-token
vocabulary. That is a far easier problem, which is why even a 0.6B
model is confident enough, most of the time, to make good choices
inside that reduced space. Priming removes an entire further class of
mistakes by never even asking the model to produce the fixed JSON
punctuation in the first place.

### What would change with a larger model

The **structural guarantee would not improve at all** — it is already
100% by construction (masking), independent of model size; a bigger
model cannot make the JSON "more valid".

What would improve is the *semantic* quality of the choices made inside
the allowed candidate set: better disambiguation on trickier or more
ambiguous prompts, more precise values (e.g. a tighter regex), and
likely fewer degenerate greedy loops like the one in Challenges faced —
larger models tend to have less peaked, better-calibrated logit
distributions. That said, the *specific* bug we hit was really a
decoding-implementation gap (the stop condition not accounting for BPE
token fusion), not a model-capability gap — `get_stop_token_ids` would
still be needed with a larger model, since the same tokenizer-merging
behaviour applies regardless of model size.

The trade-off is cost: a larger model makes every forward pass
significantly more expensive, and forcing already accounts for most of
the model calls in this pipeline (124 of them, see Terminology). This is
exactly the point the subject makes: constrained decoding lets a tiny,
cheap model reach reliability that would otherwise require paying for a
much bigger one.

### Model size vs. hardware requirements

(See "GPU vs. CPU" and "CUDA" in Terminology for what these are and why
matrix multiplication favors a GPU.)

Weights alone need roughly `2 bytes × parameter count` in fp16.
`Qwen/Qwen3-0.6B` is ~1.2 GB — small enough to run on a CPU, or
comfortably inside the 6 GB of VRAM on the RTX 4050 Laptop GPU this
project happened to be timed on above. A 70B-parameter hosted model
needs ~140 GB just for its weights — far beyond a single consumer GPU,
requiring multiple datacenter-class GPUs (e.g. several 80 GB NVIDIA
A100/H100s) just to hold it in memory before processing a single token,
with the electrical draw to match, continuously, for every call.

That is the concrete version of "how much we save": this project's
model does not need a dedicated GPU to be fast enough at all (it merely
happened to use a small laptop GPU here), while a large-model equivalent
of the same subtask needs multiple top-tier datacenter GPUs just to
exist, before even counting the energy spent serving every call to it.

### Is it worth delegating this to a small local model in an agent pipeline?

Picture a system built around one or more large hosted agents (e.g.
Claude, ChatGPT/GPT, Mistral Large) doing the reasoning and planning,
where one step along the way is "turn this request into a tool/function
call".
Pushing that specific step down to a small local model with constrained
decoding, instead of asking the large model to do it, is a good trade —
but only for that step, not for the whole pipeline:

**Where it wins:**
- **Cost and energy**: a forward pass through a 0.6B model is orders of
  magnitude cheaper — in compute, and therefore energy — than one
  through a 70B+ hosted model, and constrained decoding still needs one
  forward pass per generated token (124 of them for this project's full
  batch, see Terminology). In an agent loop that reformats results into
  tool calls repeatedly, that difference compounds fast, and it is spent
  locally instead of billed per token to a hosted API.
- **Latency**: no network round trip to a hosted API, and a much smaller
  matrix multiplication per step — noticeable when this step sits inside
  a longer, sequential agent loop.
- **A harder reliability guarantee, not just a cheaper one**: constrained
  decoding makes invalid tokens *unreachable*, not just unlikely — a
  stronger guarantee than trusting a large general-purpose model's own
  JSON-mode/function-calling to never slip, for exactly the narrow,
  fully-specified schemas this technique targets.

**Where it loses:**
- It only works when the target schema is known and enumerable ahead of
  time (fixed function names, typed parameters). It cannot help with the
  actual reasoning, planning, or disambiguation a large agent does — it
  is a leaf-node optimization, not a replacement for the orchestrator.
- Constrained decoding **guarantees validity, not correctness**: a small
  model can still confidently pick a validly-typed but semantically weak
  value inside the allowed candidates (this project's own
  repetition-loop bug is exactly that class of failure). A bigger model
  would still make better semantic choices there.
- Building and maintaining the masking logic (character classes,
  BPE-aware stop-token sets, etc., see Challenges faced) is real
  engineering work, compared to calling a hosted model's built-in
  function-calling feature. It pays off mainly once call volume is high
  enough to amortize that cost.

Net take: in an agent pipeline, offloading specifically the
*structured-output formatting* step — not the reasoning — to a small
local constrained-decoding model is the better call for cost, energy,
and latency, as long as the schema is fixed and volume justifies the
extra engineering. That is exactly the "function calling" pattern this
project is about.

## Challenges faced

The hardest bug was a token-repetition loop while generating `string`
parameters (specifically the `regex` argument of
`fn_substitute_string_with_regex`): the model would repeat a short
pattern (e.g. `cat.*cat.*cat.*...`) forever and never close the string,
hitting the `max_tokens` safety cap.

Instrumenting the generation loop to print each chosen token showed the
real cause: the BPE tokenizer often *fuses* the closing quote with the
character that follows it (e.g. `'",'` for quote+comma as one token).
The original stop condition only recognised the *lone* `"` token as
"stop", so every fused variant was masked out along with the rest of the
quote-containing tokens — the model's actual preferred token to close the
string was never a valid candidate, and greedy decoding fell back to a
worse choice that happened to loop.

The fix, `get_stop_token_ids`, computes the *set* of every vocabulary
token that starts with the same text as the reference stop token (not
just that one token id), and treats picking any of them as the signal to
stop. This was verified by generating the same parameter fully
unconstrained (plain argmax over the whole vocabulary) and confirming
the model naturally chose the fused `'",'` token immediately after the
correct value — the fix makes the constrained path match that behaviour
while still guaranteeing a valid, parseable string.

## Testing strategy

The implementation was validated by running the full pipeline against
the provided `function_calling_tests.json` and checking every output by
hand against the prompt (right function, right argument values, right
types). The repetition-loop bug above was diagnosed with small,
throwaway scripts that reused the real project functions up to the
failing point and then printed the model's chosen token id and text at
every generation step, to see the actual failure live instead of
guessing from the exception message alone.
